# Database

PostgreSQL, accessed via async SQLAlchemy 2.0, schema managed by Alembic.
The database is reachable only from the `backend` container over the
internal Docker network — it is never exposed to the public internet
(see `docker-compose.yml`, no `ports:` mapping on the `postgres` service).

## Core tables

| Table | Purpose |
|---|---|
| `users` | Accounts: email, Argon2id password hash, MFA flags, lockout state |
| `roles` | Named permission bundles; `is_system_role` protects seeded roles from deletion |
| `permissions` | Dot-notation permission codes (e.g. `finance.expense.approve`) |
| `user_roles`, `role_permissions` | Many-to-many association tables |
| `sessions` | Hashed refresh tokens; supports logout / logout-all |
| `mfa_credentials` | Encrypted TOTP secrets |
| `recovery_codes` | Hashed one-time MFA recovery codes |
| `audit_logs` | Append-only business action log |
| `security_logs` | Append-only auth/security event log (separate from audit_logs) |
| `notifications` | In-app notifications, scoped per user |

## Finance tables

| Table | Purpose |
|---|---|
| `expense_categories` | Self-referencing hierarchy (`parent_id`), soft-delete via `is_archived` |
| `expenses` | Current state of each expense (denormalized for fast reads) |
| `expense_versions` | Append-only snapshot of expense fields at each version — never updated/deleted |
| `expense_approvals` | Append-only log of submit/approve/reject/cancel/resubmit actions |
| `expense_attachments` | File metadata only; bytes live in the storage backend (see security-model.md) |

## Append-only tables

`audit_logs`, `security_logs`, `expense_versions`, and `expense_approvals`
are intentionally append-only:

- No service method anywhere updates or deletes rows in these tables.
- The initial migration (`0001_initial_schema.py`) additionally issues a
  `REVOKE UPDATE, DELETE` against these four tables for the `app_user`
  database role, if that role exists — a second, DB-level enforcement
  layer independent of application code correctness.

## Versioning and rollback

`expenses.current_version` always points at the latest `expense_versions`
row. Restoring an old version (`POST /finance/expenses/{id}/restore`)
does **not** rewrite or delete any existing version row — it copies the
target version's field values into a **brand new** version row (e.g.
restoring V1 after V1→V2→V3 produces V4, not a rewritten V1). This keeps
the full audit trail intact; see `app/modules/finance/expenses/service.py`
`restore_version()` for the exact logic, and
`tests/test_finance/test_expense_workflow.py` for the test that locks
this behavior in.

## Migrations

```bash
# Generate a new migration after changing models
docker compose exec backend alembic revision --autogenerate -m "describe the change"

# Apply migrations
docker compose exec backend alembic upgrade head

# Roll back one migration
docker compose exec backend alembic downgrade -1
```

Always review autogenerated migrations before applying them — Alembic
does not reliably detect every schema change (e.g. some constraint or
index renames), and a migration should never silently drop a column that
still holds data without an explicit, reviewed decision to do so.

## IDs

All primary keys are UUIDv4, not sequential integers — this avoids
leaking business volume (e.g. total expense count) through predictable
URLs like `/expenses/1042`, and makes object enumeration attacks
impractical.
